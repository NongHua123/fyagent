# 02 — 现状分析与代码证据

## 1. 核查范围与方法

本分析基于用户上传源码快照，不依赖私有 Git 历史。核查方法包括：

- 阅读 React 组件、Hooks、Tauri API 包装和查询层；
- 阅读 Rust 服务、平台实现、安装器模板、Capabilities 与发布工作流；
- 对照项目现有单元测试和错误类型；
- 使用官方资料验证第三方配置格式、Windows 权限语义和测试框架能力。

路径和行号均基于本次 ZIP 解压后的源码，后续代码修改可能使行号变化；文件和符号名称应作为主要定位依据。

## 3. Codex 重启现状

### 3.1 非唯一状态被降级为 Toast

**[源码事实]** `src/types/codexDesktop.ts:52-63` 已定义：

```ts
{ state: "ambiguous", reason: "installations" | "instances" | "identity_verification" }
```

说明后端协议已经能区分三个非唯一原因。

**[源码事实]** `src/hooks/useCodexRestartCoordinator.ts:41-60` 将 `ambiguous` 映射到信息 Toast，其中默认中文为：

> `配置已保存；无法唯一确认正在运行的 Codex Desktop，请手动重启。`

**[源码事实]** `notifyLiveConfigChanged()` 在 `src/hooks/useCodexRestartCoordinator.ts:118-143` 中，只有 `runtime.state === "running"` 才打开重启对话框；`ambiguous`、`unsupported` 和异常都进入手动提示。

**问题结论：** 当前实现确实把需要用户决策的“非唯一”状态处理成弱提示，与已确认需求冲突。

### 3.2 当前强制流程要求唯一目标，并有两次确认

**[源码事实]** `src-tauri/src/services/codex_desktop/mod.rs:300-350` 的 `request_restart()`：

1. 要求 `inspect_runtime_target()` 返回一个唯一目标；
2. 先调用 `request_graceful_shutdown()`；
3. 等待退出；
4. 超时后生成 `force_confirmation_required` 令牌。

**[源码事实]** `continue_restart_with_force()` 位于同文件约 `352-406`，只有第二次确认后才强制关闭。

**[源码事实]** 前端 `CodexRestartDialogState` 为：

```ts
{ kind: "restart" } | { kind: "force", token: string }
```

`requestRestart()` 和 `confirmForceRestart()` 分别执行第一、第二阶段。

**问题结论：** 本次需求不是在当前对话框上增加一个按钮，而是要将状态机从“唯一目标 + 正常退出 + 第二次强制确认”改为“精确应用身份集合 + 一次确认 + 批量强制关闭”。

### 3.3 当前平台检查会丢失候选集合

**[源码事实]** `src-tauri/src/codex_desktop/platform.rs` 的运行检查抽象使用 `RuntimeInspection::Ambiguous` 表示歧义，但不向服务层返回候选集合。

**[源码事实]** Windows `src-tauri/src/codex_desktop/platform/windows/runtime.rs:64-96` 发现多个顶层窗口时直接返回 `Ambiguous`。多个窗口可能仍属于同一个进程，因此当前抽象无法表达“多个窗口、一个进程”和“多个进程”的区别。

**[源码事实]** macOS `src-tauri/src/codex_desktop/platform/macos/bundle.rs` 会验证 Bundle ID、路径、运行实例等；候选数不是 1 时返回 `Ambiguous`。

**工程影响：** 平台层需要返回候选集合和应用级证据，而不是只返回一个布尔式歧义结果。候选的 PID、句柄、路径仍只能留在 Rust 私有类型中。

### 3.4 当前测试固定了旧安全不变量

**[源码事实]** `src-tauri/src/services/codex_desktop/mod.rs` 测试 `ambiguous_runtime_is_unavailable_and_never_receives_shutdown_or_launch` 断言歧义状态下关闭、强制关闭和启动调用全部为零。

**工程影响：** 该测试不能简单删除，应替换为更明确的组测试：

- 精确应用身份的多实例可强制关闭；
- 无精确应用身份的 `untrusted_target` 仍不得关闭；
- 全部实例关闭后只启动一次；
- 任一关闭失败时启动次数为零。

### 3.5 当前应用身份与产品改名

**[源码事实]** `src-tauri/src/codex_desktop/platform.rs` 当前白名单仍包含 Windows `OpenAI.Codex` 和 macOS `com.openai.codex`。

**[官方事实]** OpenAI 于 2026-07-09 宣布 Codex 应用并入新的 ChatGPT 桌面应用；原 Codex 应用更新后变成新的 ChatGPT 桌面应用，原 ChatGPT 桌面应用改名为 ChatGPT Classic。

**工程影响：** 实施前必须用目标发布包/实机确认新版应用的实际 PFN、Bundle ID 和安装信息。产品文案可以更新，但后端绝不能因为显示名变成 ChatGPT 就改为模糊匹配 `ChatGPT`。

## 4. WorkBuddy 现状

### 4.1 状态接口只有数量，没有模型 ID

**[源码事实]** Rust DTO `src-tauri/src/services/workbuddy/types.rs:27-36` 的 `WorkBuddyStatus` 只有：

```text
path、exists、model_count、revision、backup_exists
```

**[源码事实]** 前端 `src/lib/api/workbuddy.ts:3-9` 同样只暴露模型数量。

**[源码事实]** `src/lib/query/workbuddy.ts` 注释明确将状态查询限定为非敏感元数据，不读取模型列表和凭据。

**问题结论：** “查看目前已经存在的模型”不能通过 UI 拼装完成，必须新增独立、只返回去重 ID 的后端接口。现有状态接口继续保持元数据职责更清晰。

### 4.2 保存后明确清空 API Key

**[源码事实]** `src/components/workbuddy/WorkBuddyPage.tsx:249-262` 的保存成功分支执行：

```ts
apiKeyRef.current = "";
setApiKey("");
```

**问题结论：** 当前代码与“保存配置 API Key 不清空”直接冲突。移除这两行并不足够，还需保证 Query 缓存、错误对象和重新挂载不会持久化或回填 Key。

### 4.3 当前模型列表无搜索

**[源码事实]** 获取模型后，页面直接将返回数组存入 `fetchedModels`，并默认全选。

**[源码事实]** `WorkBuddyPage.tsx` 远程模型区域直接 `.map()` 渲染全部条目，没有搜索状态、过滤派生值或搜索输入。

**问题结论：** 搜索应作为前端派生状态实现，不需要新增后端搜索 API。

### 4.4 项目已有可复用选择算法

**[源码事实]** `src/components/usage/ModelsDevAutoSyncPanel.tsx` 已实现：

- `useMemo` 即时过滤；
- `Set` 维护选择；
- 对当前过滤结果全选/取消；
- 搜索隐藏项保留原选择。

**工程结论：** 应抽取共享 Hook 或行为模块，而不是在 WorkBuddy 复制一套近似逻辑；模型行组件不必强行通用，因为两个页面的行语义不同。

### 4.5 当前只接受根数组

**[源码事实]** `src-tauri/src/services/workbuddy/config.rs:180-223`：

```rust
let entries = value
    .as_array()
    .ok_or_else(|| WorkBuddyError::new(WorkBuddyErrorCode::ConfigRootNotArray))?;
```

**[官方事实]** 2026-06-09 版本的 WorkBuddy 配置示例使用：

```json
{
  "models": [ ... ]
}
```

文件路径仍为 Windows `C:\Users\<user>\.workbuddy\models.json`，macOS/Linux `~/.workbuddy/models.json`。

**问题结论：** 当前实现会把现行官方示例判定为 `CONFIG_ROOT_NOT_ARRAY`。双结构兼容是必要修改，不是可选优化。

### 4.6 当前冲突只在重复两次以上时触发

**[源码事实]** `config.rs:241-269` 的 `target_duplicate_ids()` 仅在 `count > 1` 时返回冲突。

**[源码事实]** 目标 ID 仅存在一次时，当前保存会直接更新，不询问用户。

**问题结论：** 已确认产品语义是“只要 ID 已存在就进入覆盖确认”，因此现有 `DuplicatePolicy`、`DuplicateModelId` 和错误码都应改为“已有模型覆盖”语义。

### 4.7 当前覆盖范围过宽

**[源码事实]** `config.rs:281-322` 的 `apply_managed_fields()` 会改写：

- `name`
- `vendor`
- `url`
- `apiKey`
- 工具、图片、推理能力
- `useCustomProtocol`
- `reasoning` 子字段

并删除 `onlyReasoning`。

**问题结论：** 当前表单只能确定连接 URL 和 API Key，不能推断已有模型能力。覆盖路径需要与新建模板分离：新建条目可以应用模板，已有条目只能补丁 `url` 和 `apiKey`。

### 4.8 API Key 保留/清空算法已有部分基础

**[源码事实]** `config.rs:324-336` 的 `managed_api_key()` 已支持：

- 非空新 Key 覆盖；
- `clear_existing_api_keys` 为真时清空；
- 否则保留原 Key。

**工程结论：** 该函数语义可复用，但应仅在“更新已有条目”路径使用；新建条目需明确返回当前 Key 或空值。

### 4.9 原子写入和 revision 可保留

**[源码事实]** `config.rs:347-364` 使用进程内随机 HMAC 密钥生成不透明 revision。

**[源码事实]** `config.rs:366` 起使用同目录临时文件、flush、`sync_all`、替换和父目录同步；Unix 临时文件权限为 `0600`。

**[源码事实]** `serde_json` 已启用 `preserve_order`，项目也已有 `indexmap`。

**工程结论：** 无需重写整个 WorkBuddy 服务。应保留 revision、备份和原子替换，重构文档解析、覆盖检测和序列化形状即可。

## 5. WorkBuddy 页面布局现状

### 5.1 大面积白边来源

**[源码事实]** `src/components/workbuddy/WorkBuddyPage.tsx` 根节点使用：

```tsx
<div className="mx-auto w-full max-w-4xl space-y-5 px-4 py-6 sm:px-6">
```

窗口宽于 `max-w-4xl` 后，内容始终居中窄栏，左右出现大面积空白。

**[源码事实]** Provider 主页面使用 `flex-1 min-h-0 overflow-hidden` 和内部 `overflow-y-auto` 的全宽页面壳层。

**问题结论：** 白边是页面壳层不一致造成的结构问题，不应通过改背景色掩盖。

### 5.2 顶部栏位移来源

**[源码事实]** `src/App.tsx:1401-1404` 的父容器为：

```tsx
<div className="flex flex-1 min-w-0 overflow-x-hidden ...">
  <div className="flex shrink-0 items-center gap-1.5 ml-auto">
```

**[源码事实]** `AppSwitcher` 后方的 Provider 上下文操作和 `+` 由 `!isWorkBuddyActive` 条件整体移除。

**问题结论：** 整个右对齐组宽度变化，导致 AppSwitcher 锚点移动。动画组件只能改变淡入淡出，不会保持几何锚点。

### 5.3 `+` 被遮挡来源

**[源码事实]** `src/components/AppSwitcher.tsx:22-32` 当前有九个应用。

**[源码事实]** `AppSwitcher.tsx:78-134` 把所有可见应用作为固定 padding 的内联按钮渲染，没有父宽度测量或 More 菜单。

**[源码事实]** `+` 位于同一 `shrink-0` 组末端，父级又使用 `overflow-x-hidden`。

**问题结论：** 宽度不足时，整个不可收缩组超出父容器，最末端的 `+` 被裁剪。提高 z-index 无法解决；必须重排结构并实现确定性收纳。

## 6. Codex 版本显示现状

### 6.1 远程版本状态被空值合并

**[源码事实]** `src/components/codex/CodexDesktopInstallerCard.tsx:193-199`：

```tsx
{remoteVersion ?? t("codexDesktop.details.unavailable")}
```

首次请求、自动重试、最终失败、无平台版本等状态都会先表现为同一个空值。

### 6.2 本地版本有同类问题

**[源码事实]** 同文件 `185-191`：

```tsx
{localVersion ?? t("common.notInstalled")}
```

检测尚未结束时可能短暂显示“未安装”。

### 6.3 查询层已有状态，但视图模型丢失

**[源码事实]** `useCodexDesktopInstaller.ts` 最终只向组件暴露 `isRefreshing: remoteQuery.isFetching`，没有区分首次加载、后台刷新、首次失败和刷新失败。

**[官方事实]** TanStack Query 5 已提供 `isLoading`、`isLoadingError`、`isRefetching`、`isRefetchError`、`data` 等状态。

**问题结论：** 不需要重写查询库，只需在 Hook 中派生显式字段状态并交给组件渲染。

## 7. Windows 权限与发布现状

### 7.1 主程序当前没有 `requireAdministrator`

**[源码事实]** `src-tauri/build.rs` 直接调用 `tauri_build::build()`；现有 `common-controls.manifest` 只声明 Common Controls v6。

**[官方事实]** Windows 清单 `requireAdministrator` 会要求应用以管理员权限运行，非管理员启动上下文会在进程创建前触发凭据或确认流程。

**工程影响：** 正式构建需要独立的 Windows 应用清单；测试构建不能机械复用同一提升清单，否则本地开发和自动测试会持续触发 UAC。

### 7.2 当前安装器是 per-user

**[源码事实]** `src-tauri/wix/per-user-main.wxs:23-30`：

```xml
InstallScope="perUser"
InstallPrivileges="limited"
```

安装目录位于当前用户 LocalAppData。模板已经包含 `WIXUI_INSTALLDIR`，具备目录选择基础。

**[官方事实]** Tauri 文档说明 per-machine 安装需要管理员权限，默认放入 Program Files；也支持自定义安装器模板。

**工程影响：** 可将现有模板改造为 per-machine，并保留目录选择，但必须新增安全路径和 ACL 验证。

### 7.3 当前发布仍生成 Portable 且无 Windows 签名门禁

**[源码事实]** `.github/workflows/release.yml` Windows 发布步骤会打包 MSI，并生成 `Windows-Portable.zip`。

**[源码事实]** 工作流包含 Apple 签名配置，但没有对应 Windows Authenticode 签名和发布前验证门禁。

**问题结论：** 正式 EXE 将长期以管理员权限运行时，Portable 从下载目录提权运行不可接受；签名也必须从“可选”升级为发布前置条件。

### 7.4 外部进程会继承调用进程安全上下文

**[源码事实]** 项目存在大量 `Command::new`、PowerShell、cmd、npm/pnpm/bun、终端和第三方工具启动调用。

**[官方事实]** Windows `CreateProcessW` 默认让新进程运行在调用进程的安全上下文中。

**问题结论：** 主进程提升后，若不新增统一降权启动层，浏览器、终端、编辑器和普通工具会意外成为管理员进程。

### 7.5 外链当前由管理员进程直接打开

**[源码事实]** `src-tauri/src/commands/misc.rs:21-35` 的 `open_external()` 直接调用 `tauri_plugin_opener`。

**[官方事实]** Microsoft 提供从 Explorer 进程调用 `ShellExecute` 的方案，专门用于从提升进程启动非提升进程。

**工程影响：** Windows 的 `open_external` 应切换到 Explorer 代理；WorkBuddy 官网和项目现有所有 HTTP/HTTPS 外链应共用同一安全路径。

### 7.6 当前开机自启支持 Windows

**[源码事实]** `src-tauri/src/auto_launch.rs` 使用 `AutoLaunchBuilder`，Windows 通过当前用户启动项启用。

**问题结论：** 主程序变为 `requireAdministrator` 后，现有启动项不再符合稳定和安全预期；Windows 应禁用并清理，其他平台保留。

### 7.7 当前单实例拦截发生在业务构建流程内

**[源码事实]** `src-tauri/src/lib.rs:330-398` 注册 `tauri_plugin_single_instance`，回调处理深链接并显示现有窗口。

**[源码事实]** UAC 在应用代码执行前发生，因此重复点击或深链接仍会先创建一个提升进程，之后插件才能转发。

**工程影响：** “不允许第二个实例”只能定义为不允许第二个业务实例。Windows 需要更早的命名互斥体和最小激活通道，使第二进程在数据库、WebView、托盘和代理初始化前退出。

### 7.8 当前 Capability 与命令面较宽

**[源码事实]** `src-tauri/capabilities/default.json` 为主窗口启用一组默认权限。

**[源码事实]** `src-tauri/src/lib.rs` 的 `invoke_handler` 注册大量配置写入、外部进程、安装、凭据和桌面控制命令。

**[源码事实]** 当前 CSP 允许 `img-src` 和 `connect-src` 使用广泛的 `https:`、`http:`。

**[官方事实]** Tauri Capabilities 用于约束特定窗口/WebView 的权限；同一窗口参与多个 Capability 时权限会合并。

**问题结论：** 主进程提升后，必须把 IPC 审核作为本次安全整改的一部分，不能只保护新增命令。

## 8. 可直接复用的现有能力

| 现有能力 | 可复用方式 |
|---|---|
| WorkBuddy revision HMAC | 继续作为乐观并发令牌，确认前后重新校验 |
| WorkBuddy 同目录临时文件与替换 | 保留，扩展为双根结构序列化 |
| WorkBuddy 单份备份 | 保留，不因新增覆盖逻辑改变备份时序 |
| `clearExistingApiKeys` | 保留语义，重命名并限制到覆盖路径 |
| `ModelsDevAutoSyncPanel` 过滤/选择 | 抽取共享 Hook 与工具栏 |
| 项目现有 UI 原语 | 直接复用，不新增同类基础组件 |
| Codex opaque force token | 改造为一次确认后的“重启能力令牌”，仍保持不透明、短期、一次性 |
| Codex 平台安装验证 | 继续用于选择可启动安装；运行候选集合另行建模 |
| TanStack Query 状态 | 在 Hook 中映射为版本字段判别联合 |
| WorkBuddy `open_external` 前端包装 | 继续使用统一命令，Windows 后端改为非提升打开 |
| window-state 保存 | 保留持久化，但改为受控恢复和运行时钳制 |

## 10. 分析结论

1. 本次多数问题是状态与边界建模问题，不是单纯改文案或 CSS；
2. WorkBuddy 服务已有可靠的 revision、备份和原子写基础，应增量重构而不是推倒重写；
3. 顶部栏必须同时解决控件顺序、容量测量、溢出优先级和窗口工作区，单独提高最小宽度不足以长期解决；
4. Windows 启动即管理员会改变整个进程树和 WebView 命令面的风险等级，安装、签名、降权启动和 IPC 收敛必须作为同一组工作完成；
5. 用户界面应保持简单，但内部必须保留充分的结构化状态和脱敏证据，以便测试与排障。
