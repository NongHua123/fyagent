# WSL Development Environment Contract

## 1. Scope / Trigger

Read this contract before changing development tool versions, onboarding
instructions, WSL scripts, build/test commands, or any workflow that could
select tools from the Windows PATH. It applies to all development performed
inside WSL, not only the macOS cross-build workflow.

## 2. Signatures

The default WSL development environment is declared by:

```text
mise.toml  human-reviewed tool versions, options, targets, and tasks
mise.lock  generated linux-x64 download URLs and checksums where supported
```

WSL developers install one global mise binary. The repository requires mise
`>= 2026.8.0`; the global mise binary itself is not downloaded or installed by
project scripts.

The active versions are:

```text
Node.js 22.12.0
pnpm    10.12.3
Python  3.12.8
Rust    1.95.0 + rustfmt + clippy
```

The macOS cross-build additionally installs the Rust targets
`aarch64-apple-darwin` and `x86_64-apple-darwin` through the same mise Rust
definition.

## 3. Contracts

- The user-installed global mise is the default version manager and command
  environment for all WSL development, including macOS cross-builds. Install
  project tools with `mise install`; run commands from a mise activated shell
  or with `mise exec -- <command>`.
- `mise.toml` is the primary WSL tool-version declaration. `.node-version`,
  `package.json#packageManager`, and `rust-toolchain.toml` remain compatibility
  inputs for their ecosystems and must resolve to the same versions.
- `mise.lock` is generated by the pinned/minimum-supported mise version for
  `linux-x64`. Do not hand-edit it. Refresh it with
  `mise lock --platform linux-x64` after an intentional version change.
- Commands executed in WSL must not resolve Node, pnpm, Python, Rust, Cargo, or
  project build tools from `/mnt/<drive>` or a Windows shim. Fix PATH or invoke
  `mise exec`; do not work around UNC/cmd.exe failures with copied dependencies.
- mise manages language runtimes and portable development tools. apt remains
  responsible for native compilers, linkers, headers, and other system
  libraries that cannot be made project-local safely.
- A tool-version change must update all compatibility declarations, regenerate
  `mise.lock`, update affected documentation, and pass the environment
  consistency tests in the same change.
- Project scripts must not download a second mise binary or override
  `MISE_DATA_DIR`, `MISE_CACHE_DIR`, `MISE_STATE_DIR`, `MISE_CARGO_HOME`,
  `MISE_RUSTUP_HOME`, `CARGO_HOME`, or `RUSTUP_HOME` to create a private mise
  installation. The macOS workflow resolves the global mise path before PATH
  isolation, then invokes that absolute binary for `mise install` and
  `mise exec`.
- Native Windows, Linux CI, and macOS release workflows are not implicitly
  migrated to WSL or mise by this contract; preserve their explicit platform
  setup until a separate validated migration changes them.

## 4. Validation & Error Matrix

| Condition                                                                   | Required result                                                                   |
| --------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Global mise is missing, older than 2026.8.0, or resolves under `/mnt`       | Fail before apt, downloads, or compilation                                        |
| WSL command resolves a managed tool under `/mnt`                            | Fail setup and enter the global mise environment                                  |
| `mise.toml` differs from `.node-version`, packageManager, or Rust toolchain | Fail the consistency test                                                         |
| A version changes without a refreshed `mise.lock`                           | Reject the change                                                                 |
| A native library is unavailable through mise                                | Install/document the minimal apt package; do not add an arbitrary runtime manager |
| Existing global mise has different tools installed                          | Project `mise.toml` wins; no global tool version is assumed                       |
| Project script downloads or configures a private mise home                  | Reject; use the global mise installation                                          |

## 5. Good / Base / Bad Cases

- Good: install global mise once; in each WSL checkout run `mise install` and
  use `mise exec -- pnpm test` or an activated mise shell for daily work and
  packaging.
- Base: a native compiler or header is unavailable through mise; install the
  documented Ubuntu package while keeping language runtimes under mise.
- Bad: download another mise into a project-specific cache, allow Windows PATH
  injection, or run unmanaged tool versions outside `mise exec`.

## 6. Tests Required

- Parse `mise.toml`, `.node-version`, `package.json`, and
  `rust-toolchain.toml`; assert equivalent exact versions.
- Assert `mise.lock` contains linux-x64 URL/checksum entries for lockable tools
  and the expected Rust tool/options entry.
- Run `mise install`, then verify `node`, `pnpm`, `python`, `rustc`, `cargo`,
  rustfmt, clippy, and required Rust targets from inside the mise environment.
- In WSL packaging tests, compare `command -v` with global `mise which` and fail
  if a managed command differs or resolves below `/mnt`.
- Assert macOS scripts contain no mise download URL/checksum and do not export
  private mise, Cargo, or rustup home variables.

## 7. Wrong vs Correct

Wrong: use Windows pnpm from WSL, let `cmd.exe` interpret the UNC repository
path, or bootstrap a second private mise just for packaging.

Correct: install global mise once, trust the repository config, run
`mise install`, enter `mise exec`, and treat any remaining missing native
library as an explicit apt dependency.
